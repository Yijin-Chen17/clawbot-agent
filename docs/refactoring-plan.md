# Clawbot 业务与任务处理重构方案

以 `04ff512` 为现状基线。先统一网页、扫码微信与 Webhook 的任务写入规则，再把执行进度、未来排程和通知投递分成独立记录。首个可上线版本以三个结果验收。完成每日任务只影响指定日期，无效或重复分段提交不会扣工时，延长任务必须通过硬截止和冲突校验。

现状依据见[业务流程 PNG](current-business-flow.png)、[任务处理 PNG](current-task-processing.png)和[问题审查](business-logic-review.md)。目标行为见[更新后的业务流程](business-flow.drawio.svg)和[任务处理逻辑流架构](task-processing.drawio.svg)。

## 一、业务规则

| 场景 | 目标行为 |
| --- | --- |
| 创建与补充信息 | 网页表单直接映射为任务命令。微信先识别意图，再按命令类型校验字段。固定任务需要明确起止，或用开始时间与耗时推导结束。灵活任务可无截止。用户已填工时且模型不可用时仍可创建。 |
| 查找任务 | 优先使用界面选择或提醒关联的任务实例与分段。名称有多个匹配时列出候选，找不到目标时提示重新指定。 |
| 一次性任务与每日任务 | 一次性任务只有一个实例。每日任务按账户时区生成日期实例。打卡、漏做、取消和重开分别作用于对应日期。停止每日重复是独立命令。 |
| 排程与确认 | 自动安排未来可移动块。已开始、已执行与用户固定的块受保护。移动已向用户确认的未来时段时，给出前后差异并等待确认。拒绝或超时可采用合法备选。 |
| 工时与截止 | 硬截止要求剩余工时全部排在截止之前。无法满足时保留待办和缺口原因。软截止可以部分排入或排在截止之后，明确展示未排分钟与逾期风险。延长和改期沿用相同约束。 |
| 提醒与执行 | 计划提交后生成提醒。投递回执只更新通知状态，用户点击或回复“开始”才更新执行状态。完成、取消及重排会撤销对应的未发通知。 |
| 外部日历 | 订阅提供只读忙时。本地忽略指定事件实例可持续生效。同步失败保留上一份可用快照并显示其时间。 |

以上是实施默认值。首版继续采用邮箱验证后开放账号和 14 天滚动窗口。“已承诺”指用户明确确认过的时段，排程结果仅展示在日历上时属于自动安排。业务时区按账户保存，既有账户回填前先核对实际运行时区。每日容量、提前截止天数与第四象限规则保留为排程策略，归并算法前先记录当前实际生效值并确定变更后的默认值。

### 任务实例、分段与版本

- **任务定义**保存标题、标签、任务类型、估算工时、优先级、锁定方式及截止约束。**任务实例**保存对应业务日期、当前执行状态与版本。每日实例以任务 ID 和账户本地日期唯一。瞬时时间以 UTC 保存，本地日期、固定时刻和只填日期的截止按账户时区解释。
- **进度事件**记录命令 ID、实例 ID、动作、工时及可选分段 ID。执行状态从待执行进入进行中、已完成或已取消。允许用户直接完成未开工实例。重开恢复到待执行，追加事件并明确恢复的目标工时。记录进度、实例版本和重排请求在同一事务内提交。
- **计划**为每个账户保存当前版本。对每个实例返回已排、部分排入、待安排或有冲突，并附已分配与未分配分钟。分段使用稳定 ID。保留同一执行段时沿用 ID，终止或替换其他执行段时保留旧记录关联。按分段完成须核对实例、当前版本及有效分段，过期请求提示刷新，重复命令返回原结果。
- **计划提案**由服务端保存，包含提案 ID、受影响实例、旧时段与新时段、输入版本、有效期和处理结果。确认、拒绝与超时使用同一套当前约束。过期或输入变化时重新计算，需要确认的变化重新展示。提交客户端建议时段的旧入口改为只接受服务端提案 ID。
- **入箱和发件箱**使用 SQLite 持久化。入站按账户、渠道和上游消息 ID 去重，扫码消息批次与游标一起提交。网页写操作接收客户端重试键，重复键携带不同载荷时返回冲突。Webhook 缺少稳定消息 ID 时，从上游补齐标识才能保证重送去重。通知以实例、分段、计划变更与提醒类型定位，并保留可复用的待发记录或投递回执。

### 一次写入与异步处理

1. 校验当前账号资格，识别命令并解析目标。草稿以账户、通道和会话隔离，带版本和有效期。模型输出通过共享校验，补问时返回实际缺失字段。
2. 在事务内提交任务或进度变更、消耗关联草稿并登记重排。接口明确区分“任务已保存，排程中”“需补充”“待确认”和已提交的排程结果。现有路由优先使用适配层承接升级。[现有路由](../server/src/routes/api.ts)
3. 规划器读取账户设置、外部日历、实例和当前计划版本，在事务外计算。发布时再次检查版本，任何输入变化都使候选失效。候选有硬冲突时保留已执行历史。若新忙时已经与旧安排冲突，查询标为有冲突，暂停对应提醒，等待重算或用户处理。
4. 发布事务一次写入新计划、受影响分段和通知变更。回执只引用已提交的版本。后台投递前重新确认账号、通道、任务和时效。明确失败时退避重试，超时且无法判断时记录待核对。渠道支持幂等键时复用同一键。后台领取作业使用可恢复租约，进程退出后可接续处理。

## 三、实施批次与合并条件

| 批次 | 实施内容 | 合并前验证 |
| --- | --- | --- |
| 1. 任务写入和输入兼容 | 提取共享命令和状态转换。接通网页两入口，再接通扫码、Webhook 和设置更新。修复硬截止字段、标签、固定时段检查、目标消歧、分段扣减和字段局部更新。注册、封禁和会话撤销共用资格检查。 | 同一操作通过各入口得到一致结果。第 99 段、同名目标、相反的起止时间和只改提醒分别通过回归验证。覆盖 M01、M03、M07、M08、T01、T02、T04、T06、T11、A02、A04。 |
| 2. 实例、排程与冲突确认 | 落地日期实例与进度事件。提取统一容量和冲突判定，复用选块算法。上线计划版本、稳定分段、服务端提案和时间语义。计算结果区分容量不足、策略排除和搜索未找到。 | 开始后的块重排仍保留执行记录。插入占用后旧提案无法提交。延长不能越过硬截止。软截止部分排入有明确缺口。覆盖 T03、T05、T07–T12、C06。 |
| 3. 消息、通知与日历 | 接通入箱、游标事务和回执恢复。解绑或凭证失效时更新连接状态。拆分提醒、同步和日切作业。ICS 合并周期事件例外、取消和忙闲，仅提交校验成功且仍有效的代次。 | 在入库、计划提交和投递三个边界分别模拟进程中断。使用重复回调、乱序同步、过期提醒和跨日实例验证恢复。覆盖 M02、M04–M06、C01–C04。 |
| 4. 统一视图和备份 | 网页、微信、ICS 共用按范围查询。版本化备份支持预览和批量提交，保存原有任务约束与进度。导入按来源指纹与记录 ID 去重，避免再估时或逐项触发重排。 | 跨天分段在指定日期可查，三种读端结果一致。备份导出再导入保留硬截止和打卡，同批次重试返回逐项结果。覆盖 T13、C05、C07、C08。 |
| 并行改造模型、账务与账号管理 | 统一模型主备、用途和费率。官方调用先预留再按请求 ID 结算，零费率按零计算。重试复用可核对结果，不确定费用进入对账。兑换在事务内按 active 状态认领。个人清屏更新可见范围。模拟来信使用隔离快照。补齐邮件挑战、账号注销及配置迁移。 | 用模拟并发验证余额不足、重复结算和重复兑换。复核零价、主备切换、旧验证码、封禁、注销和管理员模拟。统一模型服务在切换生产任务调用前就绪。覆盖 A01、A03、A05–A11。 |

批次 1 可先交付能够独立回归的兼容修复。每日任务先共用旧库的 `completed_dates`，再迁移为日期实例。版本化进度、排程提案和通知恢复在同一个账户切换窗口启用。

## 四、SQLite 迁移与发布

1. **建立可恢复的备份。** 对 SQLite 使用一致性备份，连同用户附件和服务配置记录恢复范围。在隔离环境完成一次恢复演练。通过带版本的迁移新增表、索引和唯一约束，将数据迁移与服务启动时的默认值修订分开。
2. **分批回填并保留映射。** 审核每行任务与用户归属后保留旧任务 ID。一次性任务生成单实例。每日任务从 `completed_dates` 回填可确认的日期记录，并由工作时段规则生成后续实例。将可解析的旧 `schedule_blocks` 映射为分段，缺块时只在首尾合法时回填。异常区间、未知原始工时、真实开始时间与历史送达状态单独列入对账，保留原始证据。历史提醒标记用来防止补发，未确认的旧会话提案重新求解。
3. **并行试算并对账。** 用同一份脱敏快照分别计算旧计划和新计划。核对任务数、日期实例、分钟数、身份归属、锁定块、硬截止违约、占用冲突和待发通知。算法策略导致的时间差异按样例审核。旧账本余额作为期初值，使用记录与实际扣款存在差异时进对账清单。
4. **按账户切换读写与后台。** 切换窗口先暂停该账户写入和后台领取，补齐快照期间的增量，再同时切换任务写入、读取、提醒与日切。验证兼容读模型与真实数据一致后，从内部账户扩大范围。同一账户始终只有一条写入路径和一套有效的通知消费者。
5. **回退与恢复。** 发现实例丢失、重复扣减、过期提案被应用、重复推送或财务差异时暂停扩大范围。切换前可回退到原路径。已有新版本写入时，先暂停该账户并保存新事件、计划和回执。只有兼容投影通过对账后才恢复旧路径。无法无损投影时，从备份重放可验证的变更，或留在新表上修复后恢复。已得到渠道回执的通知和已结算的费用在重放时沿用原记录。

## 五、验收用例

| 验收场景 | 可观察结果 |
| --- | --- |
| 同一每日任务在网页完成今天，次日用微信完成 | 两天各有一条执行实例。重复提交当天完成复用已有记录。每日模板继续生成实例。 |
| 连续提交同一分段、指定不存在的分段、对已换版分段上报 | 合法提交只扣一次。无效请求不改剩余工时。旧版本返回可刷新并重试的结果。 |
| 将 10:00–11:00 的硬截止任务延长 30 分钟，或确认期间插入会议 | 延长命令返回约束冲突。旧提案未提交，替代方案需要重新确认。 |
| 任务开始或完成后触发无关任务重排 | 已开始、已做的分段与进度历史可查。保留的分段 ID 和投递回执一致，完成后对应的未发提醒已撤销。 |
| 同一微信消息重送，或在保存游标后立即重启 | 已入箱命令可恢复，有上游 ID 的同一消息只生效一次，已有回执可查询。 |
| 日历例外改期、取消、同步超时及较旧同步晚到 | 日程实例按规则合并，失败保留上一份可用快照。旧代次不能覆盖新快照。计划与视图引用同一份成功快照。 |
| 网关明确失败、超时或已解绑 | 可区分重试、结果未知和过期。失败投递不推进实例执行状态。 |
| 并发兑换、零费率调用、重复导入 | 同一个兑换码只入账一次，零费率扣零，重复导入得到可核对的跳过结果。 |

沿用现有[排程测试](../server/src/services/scheduler.test.ts)、[优先级测试](../server/src/utils/priorityAlgorithm.test.ts)、[固定时间测试](../server/src/services/fixedTaskTime.test.ts)和[邮件测试](../server/src/services/emailService.test.ts)。新增临时 SQLite 的接口、并发、迁移与恢复测试。微信、邮件、ICS 和模型先用可控测试响应覆盖断网、超时与乱序，再在试点账号验证实际链路。试点放量以数据对账、约束校验、重试结果和外部回执通过为准。
